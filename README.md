# box-pi

THE BOX — Pi-only tabletop basketball scoring console. Raspberry Pi 4 (brains) +
Raspberry Pi Pico W (physical buttons over UART) + referee-facing and
spectator-facing touchscreens, syncing to the shared THE BOX Supabase backend so
games it scores show up correctly on the existing website and app.

This is a clean rewrite in its own repo — not a copy of the old `BOXV2-TEST`
pi-daemon. See `shared/wire-contract.js` for the event/data shapes this device
must stay compatible with.

## Progress log
- [2026-09-12] Repo created (`git init`), `.gitignore` added. Started `shared/wire-contract.js` — defines every cloud (Supabase) and LAN (daemon↔touchscreen) event name and payload shape as JSDoc typedefs + constants, no logic yet. Cloud side copies the existing website's event/field names exactly (frozen); LAN side is this project's own design.
- [2026-09-12] Added root `package.json` (`"type": "module"`) — needed so plain `.js` files actually resolve as ES modules when one imports another; without it Node treats them as CommonJS by default and imports fail.
- [2026-09-12] Built `shared/state-engine.js` — the one pure function (`reduce(state, action)`) that owns every game-state change (score, foul, timeout, clock, undo). No I/O, no Date.now(), no mutation — testable by calling it directly. Two rules worth remembering: team fouls reset every period (for the bonus), but a player's personal fouls never reset (foul-out is for the whole game); timeouts are pooled per FIBA half/OT bracket, not per period, so they only refill when the bracket itself changes. Verified with `scripts/test-state-engine.mjs` — confirmed a timeout gets rejected once a bracket's allotment is used up, a player flips `fouledOut` at their 5th foul, and `UNDO` reverts exactly one action with no redo.
- [2026-09-12] Fixed a review note in `state-engine.js`: `CLOCK_TICK` no longer creates its own UNDO point (ticks are automatic, not ref-triggered) — `UNDO` now skips past any number of ticks and reverts the last real action instead of a fraction-of-a-second-old tick. Re-verified with the same test script.
- [2026-09-12] Built `daemon/uart-bridge.js` — turns a line from the Pico into an action object, nothing more (doesn't call the reducer, doesn't touch Socket.io/Supabase). Checked the real firmware (`pico-firmware/main.py`) before writing this: the actual button board only ever sends `SCORE_A1/2/3`, `SCORE_B1/2/3`, `CLOCK_TOGGLE` (one button, not separate start/stop), `SHOT_CLOCK_24`, `UNDO`, `SETTINGS` (touchscreen lock toggle), and `PICO_READY` (boot handshake) — there's no physical foul or timeout button. `CLOCK_TOGGLE` and `SETTINGS` aren't game-state actions (the bridge isn't allowed to know if the clock is running), so they pass through as their own `CLOCK_TOGGLE`/`TOUCH_LOCK_TOGGLE` markers for later daemon glue to resolve. Has a first-class `devMode` that reads fake input from stdin instead of real serial — verified by piping 8 fake lines through it (handshake swallowed silently, 6 real messages mapped correctly, 1 garbage line logged a warning and didn't throw).
- [2026-09-12] Built `daemon/clock.js` — a drift-safe ticker that reports the REAL measured elapsed time between ticks (via `Date.now()`), not the nominal interval, fixing the old codebase's clock-drift-under-load bug. Verified with `scripts/test-clock.mjs`: 5 ticks at ~100ms intervals matched wall-clock time, and restarting after an 800ms idle gap reported ~99ms on the next tick instead of dumping the whole gap into it.
- [2026-09-12] Built `daemon/journal.js` — local (no network) crash-recovery log: every action is appended to `journal.ndjson` with a synchronous write + `fsyncSync` so it survives a process kill or power blip the instant `recordAction()` returns; every 50 actions (configurable) the full state gets written to `snapshot.json` and the journal is truncated, so replay after a crash is always bounded to "since the last snapshot," not the whole game. `reconstructState()` is the only place this module talks to `shared/state-engine.js` (`reduce` + `createEmptyState`) — it folds the journal back over the snapshot to rebuild exact state. Verified with `scripts/test-journal.mjs`: same-process reconstruction, a simulated crash (a fresh `createJournal()` on the same directory reconstructing purely from disk), a forced snapshot rotation, reconstruction combining the new snapshot with post-rotation actions, and a second simulated crash after rotation still reconstructing correctly — plus `clear()` removing the snapshot and resetting the journal to empty. Runtime `data/`/`data-test/` dirs are gitignored.
- [2026-09-12] Verified the real Supabase schema live (restored the paused `eoowagimooxsqcrrihbw` project to check) before writing any cloud code. Found real drift worth remembering: `games.status` only allows `'live'|'finished'|'completed'` (not `'archived'`); `game_actions.action_type` has no DB constraint but IS a closed de facto vocabulary the website/app actually filter on (`foul`/`timeout`/`rebound`/`steal`/`turnover`/`block`/`assist`/`substitution`/`jumpball`/`foul_drawn`) — of state-engine's own actions, only FOUL and TIMEOUT map onto it; `shot_events.client_event_id` exists but has no unique constraint, so it can't provide real write-idempotency yet; `games` UPDATE/DELETE are RLS-gated on `hostId = auth.uid()`, confirming this daemon can only ever work with a service-role client, never a browser-style session. Also caught a real gap in `wire-contract.js`: `GamesDataSettings` was missing `shotClockDuration` — added it.
- [2026-09-12] Built `daemon/cloud-sync.js` (Part A) — the one function (`onStateChange(newState, action)`) everything calls after `reduce()`: translates state into the frozen `CLOUD_EVENTS` payloads, broadcasts only what actually changed (`score_update` diffed field-by-field; `clock_tick` throttled to ~1/sec regardless of internal tick rate — a `FOUL` never triggers a spurious tick), persists `games.data`, and writes `game_actions` rows for foul/timeout and `shot_events` rows for attributed scores in non-quick mode (the real fix for the old daemon never writing `game_actions`). Failed writes queue for a 15s retry instead of crashing or vanishing. Verified live: 30 ticks over 3 real seconds produced exactly 3 `clock_tick` broadcasts, a foul broadcast only `score_update`, and a rejected no-op broadcast nothing. The actual authenticated write path is verified structurally (mocked client, correct table/row shapes) pending the real `SUPABASE_SERVICE_KEY` in `daemon/.env`, which Shrujal will add later — `daemon/.env` currently only has the public anon key (used for the read-only cloud-fallback test below).
- [2026-09-12] Built `daemon/resume.js` (Part B) — boot recovery: try the local journal first (`reconstructState()`, no network at all), fall back to the cloud `games` row if the journal has nothing but Supabase shows the game still live (coarse — last snapshot only, no roster), else start fresh. Verified against the real database: a live test row inserted directly via SQL (code `BXPI`, cleaned up after) was correctly reconstructed through the public-anon-key read path — score, fouls, timeouts, period, possession all matched, clock always resumes paused, and roster correctly comes back empty (a real, documented limit of this fallback path, not a bug). Local-journal path separately verified with a simulated crash/restart never touching `supabaseClient` at all.
